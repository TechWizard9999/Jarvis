# Requirements and setup

This guide runs the RTK Bugfix Agent from this repository. The application uses Docker for the controller, OpenCode, Rust/Graphify worker, and GitHub publisher. The existing host OpenCode installation and its credentials are not automatically imported.

## 1. Requirements

Install or have available on the host:

- **Docker with the Compose plugin** (`docker compose`, v2 or newer), with the Docker engine running and accessible to your user. On macOS, install and start Docker Desktop using the [official Docker installation guide](https://docs.docker.com/get-started/get-docker/).
- **Git**, for cloning repositories and managing worktrees.
- **Python 3**, for the setup script.
- **A POSIX shell** and a web browser. The launcher has been tested on macOS with Apple Silicon and Docker Desktop; native Windows execution has not been verified.
- **Internet access** for image/package downloads, locked Cargo dependency fetching, GitHub issue retrieval, and hosted model requests. Repository builds and tests run offline after dependency preparation.

Check the installed tools:

```sh
docker version
docker compose version
git --version
python3 --version
```

Normal Docker usage does not require host installations of Node.js, Rust, Graphify, OpenCode, or the GitHub CLI. Hosted NVIDIA inference does not require a local GPU.

Resource settings are limits, not validated minimum hardware requirements:

- The worker defaults to a **4 GB memory limit** and **2 CPUs**.
- The OpenCode container has a separate **1 GB memory limit**. The controller and Docker engine need additional memory.
- Cargo uses one build job, and the controller supports one active repair at a time.
- Docker images, downloaded dependencies, build caches, and run evidence need disk space. No fixed minimum disk requirement or completion time has been established.

For a real repair, also have a hosted model/API key and a clean local Cargo/Rust repository with a public GitHub issue. Draft publication additionally requires a GitHub fork, publishing credential, and commit author identity.

## 2. Prepare the project

Open a terminal in this repository. On the current machine:

```sh
cd /Users/ajampani/Documents/Jarvis
./bugfix setup
```

On another machine, use the directory where you placed this project. If necessary, make the launcher executable with `chmod +x bugfix`.

Setup creates `.env`, `.secrets/`, `repos/`, and `state/`. It preserves an existing `.env` and credential files, creates missing credential files empty with private permissions, and discovers the active Unix Docker socket when creating a new configuration. It does not supply API keys or create a GitHub fork.

If Docker is missing on a Mac with Homebrew, the optional command is:

```sh
./bugfix setup --install-docker
```

Start Docker Desktop and complete its first-run prompts before proceeding. Automatic Docker installation is only implemented for the macOS/Homebrew case.

## 3. Make the target repository available

If RTK is not already cloned:

```sh
./bugfix clone
```

This clones the selected profile's upstream/base branch into the configured clone directory and preserves an existing destination. RTK's default destination is `repos/rtk`.

For an existing clone, set `BUGFIX_REPO_ROOT` in `.env` to its **parent directory**. For example, a clone at `/work/repos/rtk` needs `BUGFIX_REPO_ROOT=/work/repos`.

The target clone must:

- Have a clean working tree, including no untracked files reported by Git.
- Be inside `BUGFIX_REPO_ROOT`.
- Contain the root Cargo workspace manifest and `Cargo.lock`.
- Match the selected repository profile and pass its baseline checks.

Source symlinks and submodules are unsupported in this MVP. The original checkout's files are preserved; the application creates branches/worktrees and updates Git metadata. Historical commits must already be present locally or fetched before evaluation.

## 4. Configure `.env`

Edit the `.env` generated by setup. Use [.env.example](.env.example) as the complete reference. Do not overwrite a working `.env` by copying the example over it.

For model execution, configure:

- `BUGFIX_MODEL`: the exact `provider/model` ID from your working OpenCode setup. Replace the shipped placeholder.
- `BUGFIX_PROVIDER_BASE_URL`: your OpenAI-compatible HTTPS endpoint; the default is `https://integrate.api.nvidia.com/v1/`.
- `BUGFIX_MODEL_CONTEXT` and `BUGFIX_MODEL_MAX_OUTPUT`: limits supported by your chosen model. The example defaults are 131072 and 8192; the output limit must be smaller than the context limit.

The chosen model must support the tool calls needed by this workflow. A valid model ID/key does not establish its repair quality, account quota, or availability.

For draft publication, also configure:

- `BUGFIX_FORK`: your personal `OWNER/REPOSITORY` fork of the upstream project, such as your own RTK fork.
- `BUGFIX_GIT_NAME` and `BUGFIX_GIT_EMAIL`: your actual commit author identity.

Set the author identity before a `--no-publish` run if you might publish its result later. Verification creates the commit only when both values are set; adding them afterward does not create a missing commit for `./bugfix publish`. Replace the shipped author placeholders before running, since a non-publishing run can otherwise record them in its commit.

Check the generated absolute paths in `BUGFIX_PROJECT_DIR`, `BUGFIX_REPO_ROOT`, and `BUGFIX_STATE_DIR`. Keep them consistent with the host filesystem; Docker uses matching paths for worktrees. When using Docker Desktop, allow access to those directories if prompted.

`BUGFIX_PROJECT_DIR` must point to this project, which contains `profiles/` and `.secrets/`. If you choose custom repository or state directories, create them with write access for your user before starting Docker; setup creates only the default directories inside the project.

If reusing an existing `.env` after changing machines or Docker contexts, verify `DOCKER_SOCKET` manually: setup preserves the existing file. Inspect the active context with `docker context show` and `docker context inspect`.

## 5. Add credentials locally

Using a local editor or password manager, put:

- The NVIDIA API key in `.secrets/nvidia_api_key`.
- The GitHub publishing token in `.secrets/github_token`, if publishing is required.

Each file contains only its token. Then run:

```sh
chmod 700 .secrets
chmod 600 .env .secrets/nvidia_api_key .secrets/github_token
```

The GitHub credential must allow pushing to your fork and creating the upstream pull request. Host `gh auth login` does not authenticate the publisher container. The NVIDIA key stays in the controller; OpenCode receives a run-specific gateway token, and repository execution containers receive neither credential.

Keep credentials out of Git, issue text, screenshots, and chat. `.env`, `.secrets/`, and runtime state are already ignored by this project.

## 6. Build and start

```sh
./bugfix build
./bugfix up
```

The build creates all four images. `up` starts the controller and prints the private dashboard URL, normally on port 3210. Open that complete URL to authenticate; opening the bare URL in a new browser session can return HTTP 401.

To explore the interface without credentials or a model call:

```sh
./bugfix demo
```

The demo is visibly simulated. It does not fix RTK, run verification, or create a PR. You can perform this step before configuring the model or cloning RTK.

After changing `.env` or a repository profile, run `./bugfix up` again. After changing the Rust compiler or Docker build inputs, run `./bugfix build` first.

## 7. Check readiness

```sh
./bugfix doctor
./bugfix test
```

`doctor` checks Docker, images, the model ID format, credential-file presence, the loaded profile, and whether the repository-root directory is nonempty. It does not inspect the clone's cleanliness or validate all provider settings; those checks happen during a run. Missing live-model settings cause a nonzero exit. Publishing settings are reported separately; check them before enabling publication. A passing doctor check does not prove the model endpoint accepts your key, that the token has sufficient GitHub permissions, or that RTK's full baseline passes.

`test` runs the application tests inside the controller container and does not need real credentials. The last recorded run passed all 26 tests. See [TESTING.md](TESTING.md) for the integration evidence and what was simulated.

### Known RTK baseline blocker

On **18 October 2026**, RTK commit `e542dca0bdcc262fa035dcf7fc33910cdcc8cdaf` passed formatting but failed workspace Clippy because `src/llm_proxy.rs` repeats `#[cfg(feature = "engine")]` at lines 396 and 401. Subsequent baseline checks were not run. The application stops with `environment_blocked` when this baseline fails.

A live repair needs an upstream contribution base that passes the configured checks. Do not remove the check to hide the failure. Historical evaluation can use an inspected passing commit, but cannot publish. Consult the dated verification record rather than assuming this upstream issue is permanently present.

## 8. Run a repair

In the dashboard, enter the absolute clone path and a real GitHub issue URL. Enable draft publication only when the publishing configuration is ready.

Equivalent CLI command, producing a verified patch without publication:

```sh
./bugfix run --repo '/absolute/path/to/rtk' \
  --issue 'https://github.com/rtk-ai/rtk/issues/NUMBER' --no-publish
```

Replace the example path and `NUMBER`. For a draft PR, use `--publish` instead. Live mode fetches the configured upstream contribution branch (`develop` for RTK) and requires an open issue. The URL must belong to the selected profile's upstream repository.

For a historical evaluation:

```sh
./bugfix run --repo '/absolute/path/to/rtk' \
  --issue 'https://github.com/rtk-ai/rtk/issues/NUMBER' \
  --mode evaluation --base PRE_FIX_SHA --retrieval graph --no-publish
```

Use an inspected pre-fix commit containing the behavior you intend to reproduce. `--retrieval text` selects the text-only comparison mode. Even a valid setup can finish with `cannot_reproduce` or `verification_failed`; verification is required before publication.

## 9. Follow progress and retrieve results

These are separate actions; run the one you need:

```sh
./bugfix list              # List runs
./bugfix tail RUN_ID       # Follow one run until its outcome; Ctrl-C detaches
./bugfix cancel RUN_ID     # Stop an active repair
./bugfix publish RUN_ID    # Publish an eligible verified commit
./bugfix logs              # Follow controller logs; Ctrl-C detaches
./bugfix down              # Stop the controller
```

Replace `RUN_ID` with the ID returned when starting a run. `publish` is for an eligible, already verified live commit; it cannot publish a demo or historical evaluation. `down` stops the controller; cancel an active repair first.

The dashboard displays events, tool/check output, diff, report, and publication state. Provider-exposed reasoning is displayed when available. Evidence lives under `BUGFIX_STATE_DIR/runs/RUN_ID/`; completed runs include a report and a patch if one was produced.

If publishing fails, a verified result is retained as `verified_unpublished` where applicable. Inspect the report, correct the publishing problem, then retry. After a controller restart, interrupted repairs are recorded instead of silently resuming model actions.

## 10. Adjust resources or support another Rust project

In `.env`, configurable settings include:

- Worker limits: `BUGFIX_MEMORY`, `BUGFIX_CPUS`.
- Per-command timeout (guards against a hung build/test): `BUGFIX_COMMAND_TIMEOUT_MS`.
- Fix attempts per verification round: `BUGFIX_MAX_ATTEMPTS`. There is no token, tool-call or run-time cap.
- Deployment: `BUGFIX_PORT`, `BUGFIX_NETWORK`, image names, directories, and Docker socket.
- Compiler: `BUGFIX_RUST_TOOLCHAIN`; rebuild the worker after changing it.

To add a compatible Cargo workspace, copy [profiles/rtk.json](profiles/rtk.json) to `profiles/your-project.json`, edit its upstream/base, package/manifest, source/test/fixture roots, scope limits and check commands, and set `BUGFIX_PROFILE_NAME=your-project`. Configure a matching fork and compiler, then restart the controller. This release requires ordinary inline library tests; other languages and replacing Docker require adapter code.

## 11. Troubleshooting

- **Docker is unreachable:** start the engine; verify the active context, socket access, and `DOCKER_SOCKET` in `.env`.
- **Missing `docker-credential-desktop`:** use `./bugfix`; the launcher adds Docker Desktop's bundled tools to PATH on macOS.
- **Port conflict:** change `BUGFIX_PORT` and run `./bugfix up` again.
- **Missing key/model:** fill the private credential file and replace the model placeholder; restart and rerun `doctor`.
- **Dirty or disallowed clone:** resolve local changes and check its parent against `BUGFIX_REPO_ROOT`.
- **Dependency, compiler, or baseline failure:** inspect the run report/logs and the selected profile. Fetching needs internet; builds/tests run offline.
- **Worker killed or out of memory:** inspect Docker's allocation and the worker limit. Lowering CPU concurrency can help pressure; lowering the memory cap does not make a large build require less memory.
- **PR creation rejected:** verify fork/token capabilities and inspect the publication error. Upstream CI, maintainer review, and any CLA action are separate from local checks.

## 12. Optional development requirements

Only needed to edit/typecheck the application or run the host integration scripts:

- Node.js **24 or newer** and pnpm for development dependencies.
- Docker CLI access for container integration scripts.
- Playwright and installed Chrome for the optional browser script. `BUGFIX_PLAYWRIGHT_MODULE` can point to an existing Playwright module installation.

Run these from the project root, after building the Docker images. The TypeScript host scripts read process environment variables; they do not automatically load `.env`. The examples use Node's `--env-file` option to load it. For a custom profile in a direct Node command, set `BUGFIX_PROFILE` to the JSON file path; `BUGFIX_PROFILE_NAME` is interpreted by Compose and setup only. Keep the shipped RTK profile for the scripted repair fixture, whose assertions depend on it.

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm check
pnpm test
BUGFIX_E2E_GRAPH=1 node --env-file=.env scripts/e2e.ts
node --env-file=.env scripts/adapter-e2e.ts
node --env-file=.env scripts/publisher-e2e.ts
```

Run the repair integration before the publisher integration: the publisher test consumes its `state/integration-results.json` and verified bundle. The following separate check inspects the configured clone's current `HEAD`, including Graphify and the full baseline, without calling the model. It can return nonzero for the recorded RTK baseline blocker:

```sh
node --env-file=.env scripts/readiness.ts --baseline
```

For browser validation, first start the dashboard with `./bugfix up`. Playwright is not included in this project's development dependencies: use an existing installation through `BUGFIX_PLAYWRIGHT_MODULE`, or install it in a separate tools directory and point that variable to its `index.mjs`. With Playwright and Chrome available:

```sh
node scripts/browser-e2e.mjs
```

The repair fixture uses a scripted agent; the OpenCode integration uses a local scripted model endpoint; the publisher test uses a local Git remote and mocked GitHub responses. These do not constitute a live NVIDIA repair or a real PR. The host adapter integration has been exercised on macOS/Docker Desktop and uses `host.docker.internal`; other host networking setups need validation. Set `BUGFIX_DOCKER` when running host scripts if the Docker CLI is not on PATH.

The full architecture and configuration details are in [README.md](README.md); dated test results and the remaining live acceptance check are in [TESTING.md](TESTING.md).
